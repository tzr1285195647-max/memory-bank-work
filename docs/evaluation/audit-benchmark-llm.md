# 审计拦截率评测报告 · 真实模型层

> 评测集与方法见 [本地层报告](audit-benchmark-local.md) 与 [评测说明](README.md)。
> 本页记录双层门（规则层 + 写作审计 Agent）在真实模型下的表现。评测故事与全部编辑随仓库提交。

## 结果总览

| 配置 | 篡改拦截率 | 润色误拦率 | 模型调用降级 | 说明 |
| --- | --- | --- | --- | --- |
| 本地规则层（无模型） | 88%（22/25） | 4%（1/25） | — | 基线，见本地层报告 |
| 双层门 · deepseek-flash | 88%（22/25） | 4%（1/25） | **53 次全部失败** | 推理模型 100% 输出非法 JSON，全部降级为规则层 |
| 双层门 · deepseek-chat | 88%（22/25） | 4%（1/25） | 0 次 | 模型层全部成功决策，但未捕获规则层的 3 条漏报 |

## 发现一：推理模型不适合审计层（deepseek-flash）

deepseek-flash 是推理型模型（输出带 `reasoning_content`），在本管线的严格 JSON Schema 审计调用下
**50 条编辑的全部模型调用均返回非法 JSON**（`LLMUnavailableError: 模型输出不是合法 JSON`），
每次都触发降级到确定性规则审计。产品因此退化为单层规则门——结果与本地基线完全一致。

**建议**：审计这类需要严格结构化输出的环节应选用非推理模型（如 deepseek-chat，0 降级）；
若要使用推理模型，需为审计调用单独放宽输出约束并自行解析。

## 发现二：模型审计对高重合度数字/实体篡改不敏感（deepseek-chat）

deepseek-chat 下 27 次模型审计全部成功（0 降级），但**规则层的 3 条漏报模型层同样放行**：

| 编号 | 手法 | 规则层 | 模型层 |
| --- | --- | --- | --- |
| T04 | 十二岁改为十四岁 | 漏（汉字数字不触发 anchor；共享前缀凑满重合下限） | 漏（语义支持判断未做数值一致性核对） |
| T09 | 长句内插入「三姑」 | 漏（与原文重合度依然很高） | 漏 |
| T12 | 晒谷场改为学校操场 | 漏 | 漏 |

综合双层门总拦截率仍为 88%。这暴露了一个明确的改进方向：

1. **规则层**：anchor 正则扩展汉字数字（十二/十三/…/两）年龄与日期；
2. **模型审计 Prompt**：增加"数值与实体一致性专项核对"指令（逐项比对句中年份/年龄/地名与所引证据），
   把"语义大致相符"升级为"要素逐项相符"；
3. 以上两项均已列入 [演进路线](../ROADMAP.md) 的可信机制迭代项。

## 运行方式

```bash
# .env 配置 AGENT_MODE=llm 与模型密钥后：
python backend/audit_eval.py prepare-db   # 先停止后端
python backend/run.py                     # 启动后端（默认 8787；被占用时 .env 改 PORT）
python backend/audit_eval.py llm --base-url http://127.0.0.1:8788
```

评测判定与产品行为一致：规则层先拦（零成本），通过者进入模型审计；任何一层给出
`unsupported` 发现即 409 拒绝发布。模型层是否真正参与决策可通过 `/api/agent/status`
的 `fallbackCount` 验证（本次 deepseek-chat 全程为 0）。
